# OpenFX reliability release verification

Verified on November 5, 2026. The three changed applications were built as Vercel production containers, tested in staging, and promoted. Settlement Recon was retested on its existing public deployment.

All 14 API checks and eight browser workflows passed. Browser coverage used Chromium at 390 and 1440 pixels, checking page identity, rendered content, real interaction results, horizontal overflow, and JavaScript errors. The Browser plugin was unavailable, so the existing Playwright driver and Chromium installation were used. DataGuard previously rejected readiness immediately when a healthy background bootstrap was still running. Readiness now joins one shared completion event for up to 15 seconds and then checks current database connectivity. The fresh staged container's first readiness request returned 200 in 3.674 seconds. Four later canonical probes all returned 200. A separate isolated PostgreSQL drill verified real outage rejection, recovery, source fingerprint preservation, and concurrent startup requests. Its full PostgreSQL suite passed 199 tests with zero skips. [Fix and reproduction](https://github.com/9059Rohith/dataguard/blob/25286831df9cc3f5c562c53d9389a255f1c5c7ea/docs/readiness-cold-start.md)

FluxLake now retries transient connection and session setup failures up to three times before entering the transaction body. It logs safe phase, exception-type, SQLSTATE, and attempt fields. A real database recovery published one 100-event batch with one source invocation. A controlled acknowledgement failure after an actual commit left one invocation and the committed rows intact. The PostgreSQL suite passed 208 tests, and both 20,000-event benchmarks reproduced their expected fingerprints and exact replay results. The staging host check required a second small fix to trust only the exact validated deployment hostname supplied by Vercel. Its 64 targeted security/API tests passed, and the fresh staged deployment then returned readiness 200 in 3.286 seconds and read 200 retained real events before promotion. [Connection proof](https://github.com/9059Rohith/fluxlake/blob/e013094917bf1e6a4141ccd204fbf047dfe87613/docs/workspace-connectivity.md) · [Host boundary](https://github.com/9059Rohith/fluxlake/blob/e013094917bf1e6a4141ccd204fbf047dfe87613/docs/deployment-hosts.md)

PipeFoundry's repository metadata failure previously replaced its independent build workspace with an error. The overview now preserves configuration, validation, and manifest inspection while marking unavailable source values. The actual public mobile run encountered GitHub 429 responses for all three repository feeds and still completed the workflow. Five provider resource errors were recorded across both viewports, with zero uncaught JavaScript errors. The local regression also exercised 429 and 502 responses. Its Python suite passed 107 tests with 23 optional skips, plus six Node UI tests and four browser outage scenarios. [Fix and reproduction](https://github.com/9059Rohith/pipefoundry/blob/cfbb059334abcea62759c3d8d3d44ab0c5d88501/docs/overview-resilience.md)

The earlier FluxLake failure's precise cause remains unconfirmed because its original diagnostic evidence was unavailable. Current failures retain safe diagnostic fields. Actual database outages or bootstrap exceeding DataGuard's 15-second wait budget can return 503. GitHub quotas can return 429 and unavailable repository values. These observations establish the named workflows and fault cases on the measured environments. The retest issued zero model requests and zero cluster actions.
